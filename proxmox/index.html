Message Link Server on Proxmox

One command in the Proxmox host's shell makes a container with the server in it.

Not public yet. The install script's address and the server package aren't published yet, so the command below won't work until the first public release.

What it makes

  • An unprivileged Debian 13 container, started when the host boots.
  • Message Link Server inside it as a systemd service, with its Tailscale door.
  • With Google (the default), official Google Chrome from Google's own repository, so Google Messages, Messenger, Google Voice and Instagram can sign in on the server's page.
  • Backups can go directly to a network share chosen on the server's page, or to a folder of the Proxmox host mounted in the container. Learn more.
  • A nightly update at about 03:00 for the server and for Chrome.

Install

  1. In the Proxmox web interface, select the node and open Shell. It's a root shell on the host.

  2. Run:

    bash -c "$(curl -fsSL https://raw.githubusercontent.com/wrenchware/switchboard-messages/main/docker/messages-server/proxmox/install-proxmox.sh)"

  3. Answer its questions. Each has a default in brackets, and Enter takes it:

    Container id
    The next free one.
    Hostname
    messages-server
    Google Messages and Google Voice
    Yes. This installs Google Chrome in the container.
    Storage, disk, memory, cores
    Your storages for the template and the disk; 8 GB of disk; 4096 MB of memory with Google, 2048 without; 2 cores.
    Network
    The bridge (vmbr0), and dhcp or a fixed address such as 192.168.1.50/24. A fixed address, or a DHCP reservation, keeps the server where your devices expect it.
    Backups folder on this host
    A full path such as /mnt/backups/messages, or empty to keep backups inside the container.
    Reach the server through Tailscale
    Yes, for the phone. You can paste a Tailscale auth key here, or press Enter and sign in on the page instead.
    Page password
    Press Enter to set it on the page's first visit, with the setup code.

    It shows what it's about to make and asks once more before it changes anything.

  4. Note what it prints at the end: the page's address and the setup code. If you lose the code, it's in the server's log (put your container's number in place of <id>):

    pct exec <id> -- journalctl -u messages-server --no-pager | grep -i "setup code"

  5. Open the page it printed, https://<address>:8787/, from a browser at home, and follow the first run.

On the server's page

  1. Accept the certificate warning once: the server made its own certificate.
  2. Enter the setup code, then choose the page's password.
  3. If you have a backup, restore it before connecting accounts. Stop the old server first.
  4. Sign in to your accounts from the server's page.
  5. Sign the server in to Tailscale.
  6. Set up notifications.
  7. Add your phone: scan the code from your own server's page, check the server shown, then choose Join. Send a test notification once the phone is joined.
  8. Add a PC, and set the backup password.

Anyone with the page's password can manage the server. Joined phones and PCs read and send messages. Setup steps can be picked up later from the page. More about the first run.

Afterwards

Update
Run the same command again. It finds the container it made and updates the server in it; sign-ins, devices and data stay. The nightly update does the same once releases are published.
Watch the log
pct exec <id> -- journalctl -u messages-server -f
Change a setting
pct exec <id> -- nano /etc/messages-server/environment, then pct exec <id> -- systemctl restart messages-server
Remove it
pct stop <id> && pct destroy <id>. A backups folder on the host stays.

Options

Add them after the command with _, like bash -c "$(curl …)" _ --yes.

--yes
Take every default without asking: no page password and no auth key.
--no-google
No browser sign-in. Leave Chrome enabled to connect new accounts, including Messenger and Instagram.
--ctid <number>
The container's id.
--tarball <file or https address>
A server package to install instead of the newest release.

Good to know

  • The container has Proxmox's nesting feature on, as Proxmox does by default for new unprivileged containers. The server's own systemd isolation and Chrome's sandbox need it. The container stays unprivileged, with no device or host folder but the backups folder you choose.
  • Chrome always runs with its sandbox here. If the host's kernel doesn't let ordinary accounts make user namespaces, the script warns you and browser sign-in stays unavailable.
  • Tailscale needs nothing special from the container: the server's door runs Tailscale in userspace, with no tun device.
