Security / Details

Security details

Updated 2026-11-19, for Message Link 0.1.476 and the server image built from the same source. The plain version is Security; this page is the mechanics, with the numbers. Every value here is read from the code, and the source of the server and helpers is public.

Threat model

Message Link is built for one household running its own server. It is designed to hold up against:

  • Other devices on the home network, including a compromised smart-home gadget: they can reach the server's port but not its accounts.
  • The internet: the server answers only the home network and your tailnet, and refuses requests a reverse proxy forwarded.
  • Other apps and other user accounts on the PC or phone.
  • Hostile content: a message, link, file or web page sent by someone else.
  • A compromised dependency or build step, as far as pinning, isolation and signatures reach.

It does not try to defend against root on the server's host, malware running as your own user, or the messaging services themselves (see Limits).

How the parts fit

Stored data

Windows
Sign-ins, device secrets, the state, media and archive databases are sealed with DataProtectionProvider("LOCAL=user") (DPAPI-NG, current user). Pictures in the media cache are encrypted too.
Linux server
Every sealed value is AES-256-GCM with a 12-byte random nonce and a fixed associated-data label, under a 32-byte key file. The server refuses to use the key file if any group or other permission bit is set (0600). The TLS private key is PEM, mode 0600, in a 0700 folder on the keys volume.
History
history.db has its own random 64-byte key, sealed as above. Chat, row and message IDs are stored as HMAC-SHA256 values under one half of it; every row's payload, message text included, is AES-256-GCM under the other half, with the row's ID as associated data, so a row can't be moved to another without failing to open.
Android
The server connection (messages.server.token) and the conversation list and pending sends (messages.inbox.cache) are AES-256-GCM under AndroidKeyStore keys. allowBackup="false", and the data extraction rules exclude every domain from cloud backup and device transfer.
Backups
PBKDF2-HMAC-SHA256 with 600,000 iterations and a 16-byte salt derives an AES-256-GCM key. The file is cut into 1 MiB chunks; each nonce is an 8-byte random prefix plus a 32-bit chunk index, and each chunk's associated data is the SHA-256 of the header, the 64-bit index and a final-chunk flag. Reordered, truncated or extended files fail to open. Left out: every service sign-in, Messenger's encrypted-device database, the tailnet identity, the outbox, the operation journal, caches and logs.
Logs
Fixed-format lines: counts, states, durations and one-way tags. Library error text from the helpers passes through an allowlist or a scrubber that strips URLs, tokens and digit runs.

How devices reach the server

TLS
TLS 1.2 and 1.3 only, HTTP/1.1, on a self-signed ECDSA P-256 certificate valid for 10 years. A missing key never makes a new identity: the server refuses to start.
Pinning
Clients pin the SHA-256 of the whole certificate (DER) and compare it in constant time. The pin is the only trust: no CA store, no fallback. On Android this is a custom X509TrustManager on the one OkHttp WebSocket the app opens.
Device tokens
32 random bytes per device. The server keeps only SHA-256(token), in a sealed list, and checks a presented token against every device in constant time without stopping at the first match. Revoking closes the device's open connections.
Pairing codes
10 characters from a 31-character alphabet (no 0, 1, I, L, O), about 49.5 bits, from a CSPRNG. Single use, 10 minutes. Tries are spaced 1 s apart server-wide; per source, 3 free misses, then waits that double up to 5 minutes. IPv6 sources count per /64. On Linux the code goes to the container's output, never to server.log.
Asking to join
The device and server exchange 16-byte nonces, the server committing to its nonce (SHA-256) before seeing the device's. The code both screens show is SHA-256 over the certificate hash, both nonces and the request ID, rendered as 6 characters (about 30 bits), so a machine in the middle can't make the codes match. Approving asks for the page password. After approval the device proves it holds the 6-character finish code with HMAC-SHA256, and its token is kept only once it confirms it saved it. Limits: 4 waiting, one per source, 10 s between a source's requests, 5 minutes after a deny.
The door
At most 8 connections may be in TLS or upgrade at once, 2 per address; tailnet connections wait in a pool of their own. 5 s for the TLS handshake and headers, 8 KiB of headers, 32 header fields, no body. 64 upgraded connections in all, 4 per device (the oldest is closed). 4 MiB per WebSocket message, text only, no compression, 256 requests in flight per connection. A request carrying an Origin header is refused, so no web page can open the protocol socket.
The server's page
Password 12 characters to 128 bytes, stored as PBKDF2-HMAC-SHA256, 600,000 rounds, 16-byte salt, compared in constant time. Tries: 1 s apart server-wide, with the per-source backoff above. The session cookie is the expiry, 16 random bytes and an HMAC-SHA256 under a key that changes when you sign out everywhere; 7 days, HttpOnly; Secure; SameSite=Strict. Every POST needs Origin equal to the page, Sec-Fetch-Site absent or same-origin, and a per-session HMAC form token. Headers: default-src 'none' with scripts allowed by hash only, frame-ancestors 'none', base-uri 'none', form-action 'self', X-Frame-Options: DENY, nosniff, no-store. Sensitive actions ask for the password again unless it was typed within the last 10 minutes.
Who may reach the page
Loopback, RFC 1918, link-local and IPv6 unique-local addresses, excluding the host's own gateways (Docker's IPv6 proxy presents outside peers as the bridge gateway), or a device that came through the tailnet relay. Any request with Forwarded, X-Forwarded-*, X-Real-IP, Via, CF-Connecting-IP or True-Client-IP is refused. Message Link Server for Windows binds 127.0.0.1 only.
Tailnet
The server's tailnet door asks Tailscale who each peer is (WhoIs) and admits only the same Tailscale user, never a tagged device. If you tag the server itself, the same-user check turns off and your tailnet's access rules decide, which the log says (tailnet owner_check=off reason=tagged). The door hands each connection to the server over a Unix socket in a 0700 folder, prefixed by a strictly parsed PROXY v1 line naming the peer. Tailscale's own logging is turned off.
Push
Each phone makes a P-256 key pair in AndroidKeyStore (PURPOSE_AGREE_KEY, so the private key never leaves it) and a 16-byte auth secret. The server encrypts each notification per RFC 8291 (aes128gcm, RFC 8188), one record padded to 1,536 bytes so its length says little, and sends it through your own Firebase project. A push that doesn't decrypt is dropped.

Inside the server

Helpers
Each service is a separate Go process driven over its own stdin and stdout (anonymous pipes): no socket and no named pipe for another process to connect to. Lines into a helper are capped at 1 MiB, lines out at 8 Mi characters. Sign-ins travel only as frames on those pipes. The Linux server removes MESSAGES_ADMIN_PASSWORD and MESSAGES_TAILNET_AUTHKEY from its environment before starting any child, and the tailnet auth key goes to the door on stdin. Helpers recover from a panic in a request handler and print no tracebacks.
Downloads
Messenger and Instagram media fetches and every link preview resolve the name themselves, check every answer and dial the checked address, so DNS rebinding can't reach the LAN. Refused: private, loopback, link-local, CGNAT (100.64.0.0/10), documentation and benchmarking ranges, 240.0.0.0/4, IPv6 outside 2000::/3, 6to4 and Teredo, the host's own networks, single-label names and .local, .lan, .home, .internal. No proxy. Meta session cookies go only to Meta's own hosts (fbcdn.net, cdninstagram.com and the like), matched on a dot boundary; anything else is fetched anonymously, with at most 5 redirects. Caps: 25 MiB per media item; link previews 1 MiB of HTML, 5 MiB per image, 16,384 px a side and 40 megapixels, checked from the header before decoding.
Container
Runs as UID 2787 under tini, with --cap-drop ALL, no-new-privileges, 4 GB of memory with no extra swap and 2,048 processes. /data and /keys are 0700. No Docker socket, no host network, not privileged.
Chrome
Chrome opens only the services' sign-in pages: its managed policy blocks every URL except an allowlist of their hosts, blocks file:, chrome:, javascript: and view-source:, and turns off developer tools, remote debugging, extensions, downloads, file dialogs, password saving, autofill, sync and printing. Its sandbox needs user namespaces, which Docker's default seccomp profile refuses without a capability; install-unraid.sh adds exactly chroot, clone, setns and unshare to Docker's own profile (chrome-seccomp.json) rather than granting SYS_ADMIN. The Community Applications template, which can't ship a file, uses seccomp=unconfined with the same user and capability limits. Once a page loads, the server reads /proc and logs whether every renderer carries a seccomp filter (google chrome sandbox=active).
Linux service
The systemd unit runs as its own user with UMask=0077, NoNewPrivileges, empty capability sets, ProtectSystem=strict, ProtectHome, PrivateTmp, PrivateDevices, ProtectKernelTunables/Modules/Logs, ProtectControlGroups, ProtectClock, ProtectHostname, ProtectProc=invisible, RestrictSUIDSGID, RestrictRealtime, RestrictNamespaces, LockPersonality, native system calls only and four address families. MemoryDenyWriteExecute is left off because .NET compiles code at run time.

Your accounts with the services

Uncertain mutations
Every send, reaction, edit and removal is recorded in an operation journal before it goes out. One that was cancelled after it started, or was running when the server stopped, becomes outcome_unknown and is reported, never sent again. Clients look its outcome up; they don't resubmit it.
Pacing
Contact search waits for 3 characters and 700 ms of quiet, 900 ms per provider, with a 5-minute cache, enforced on the server whoever asks, with one search waiting at a time. Instagram: at most 5 background reads per connect and 30 an hour, a count that survives restarts and starts fully spent if it can't be read; reads devices ask for are capped at 60 a minute and 600 an hour.
Sign-in
On the PC, sign-in is a WebView2 window on the service's own page, with no host object, no web-message bridge and no injected script, downloads cancelled and DevTools off. Messenger's runs InPrivate in a profile made for that attempt. Only the named sign-in cookies are read, and their values are cleared from memory afterwards.

PC and phone

Links
Only http and https addresses with a valid host and no user info become links, plus mailto: from a strict pattern; that rules out javascript:, file:, UNC paths (which could leak NTLM hashes) and ms- handlers. A link whose words name a different site than its address is shown unlinked. Bidi and control characters from decoded entities are dropped.
Received files
File names are reduced to the name alone, invalid characters replaced, trailing dots and spaces trimmed, capped at 100 characters, and saved with Zone.Identifier ZoneId=3 (Mark of the Web) before they're moved into place. A photo set saved without a dialog is forced to a picture extension. Nothing received opens by itself.
Local IPC
The PC's pipe to its own server allows only the current user, denies the NETWORK SID, is created with FirstPipeInstance, and needs a bearer token compared in constant time. The client opens it with CurrentUserOnly, which checks the pipe's owner. The app registers no URI handler.
Android
Notification actions carry an identifier made from the conversation and a one-way hash of the device, which a PendingIntent fill-in can't change; the receiver acts only when the extras agree with it. Mark as read requires authentication. Opening a texting conversation from an outside sms: link holds its read state until you touch it. The FileProvider shares only the app's media and camera folders, read-only.
Terminal
mlink replaces every C0 control except tab and line endings, DEL and every C1 control with U+FFFD before printing message text.

Hermes Agent

Key
Sealed like a sign-in; devices learn only whether one is set. Only the server's page can set or change it, and the address takes http or https with no user info, query or fragment.
Transport
No automatic redirects (a 307 would carry the turn to another host). Buffered answers are capped at 8 MiB and a streamed reply at 64 MiB; an address that keeps sending ends the turn, not the server.
Approvals
Only once or deny is ever sent, never session or always, and only on your explicit answer. A command over 64,000 characters, or containing a control or format character other than a line break or tab (bidi overrides, zero-width marks, escapes), is shown with U+FFFD in their place and can only be denied in Message Link.
Reports
Scripts on your network may post short reports into Hermes's own thread with a 256-bit token, kept only as a hash: at most 6 a minute, 30 an hour and 200 a day per profile, wrapped as data, never starting a turn. Nothing from your other conversations reaches Hermes automatically.

Updates and the supply chain

Image
All seven base images in the Dockerfile are pinned by digest. Go builds run with GOTOOLCHAIN=local, GOFLAGS=-mod=readonly and go mod verify; .NET restores in locked mode from committed lock files, with NuGet's vulnerability audit failing the build. Google Chrome's apt key is accepted only if its fingerprint is EB4C 1BFD 4F04 2F6D DDCC EC91 7721 F63B D38B 4796.
Builds
Workflows run only on pushes to the main branch, a schedule or a manual run, never on pull requests or forks. Every action is pinned to a commit and the repository allows only GitHub's own actions and three Docker ones. The build runner reaches BuildKit through its socket alone, with no Docker socket. Dependencies are reviewed weekly; govulncheck finds no reachable vulnerability and dotnet list package --vulnerable none, as of this page's date.
Linux packages
Each release package has an SSH signature (ssh-keygen -Y, namespace message-link-package). The nightly updater and install-proxmox.sh check the .sha256 and then the signature against the key they carry, before anything is stopped. To check one yourself: 
printf 'message-link-release ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIASDuy6t9lRx7d8PjcN7n7aYxvFR9AJkzDQA1z1huRWg\n' > allowed_signers
ssh-keygen -Y verify -f allowed_signers -I message-link-release \
    -n message-link-package -s messages-server-linux-x64.tar.gz.sig < messages-server-linux-x64.tar.gz
Apps
Windows updates come only through the Microsoft Store; there is no custom updater. Android updates come through Google Play.

Limits

  • Root on the server's host, or anyone who can read its keys volume, can read everything the server holds. On Linux the TLS key and the state key are files protected by permissions, not by hardware.
  • Malware running as your Windows user can unseal what DPAPI protects for that user. That is Windows' boundary, and the app doesn't pretend otherwise.
  • The page's certificate can't be checked by a browser. Compare its fingerprint once with the line the server prints at start, or reach it through your tailnet.
  • Backups are as strong as their password: PBKDF2 slows guessing but doesn't stop it, and a server backup holds the keys to every message. Use a long passphrase.
  • Every paired device is equal. Any of them can read every conversation and answer a Hermes approval, so remove devices you no longer use.
  • Link previews are fetched from your server, so a sender can learn its public address when the conversation is opened.
  • Image signatures. Server images are pinned by digest when promoted but not signed; the Linux package is.
