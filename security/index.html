Security

Security

Updated 2026-11-19. Applies to Message Link for Windows, Message Link for Android and Message Link Server.

Message Link keeps your sign-ins to Google Messages, Messenger, Google Voice and Instagram, and copies of your messages. This page explains how each part protects them and what it can't protect against. The apps and server were last reviewed for security on 2026-11-19, and the problems found are fixed.

Summary

Your data stays on hardware you own

Wrenchware runs no servers that receive your messages or sign-ins. Your PC, your phone and your own Message Link Server talk to the services directly.

Everything kept is encrypted

Sign-ins and saved state are sealed with Windows' or Android's own key storage, or a key only the server's account can read.

Only your devices can reach your server

Each device is approved by you, holds its own secret, and checks it is talking to your server and no other.

Each service runs on its own

Every messaging service runs in a separate helper program, and a web page the server opens runs in Chrome's sandbox.

Uncertain sends are never repeated

A send whose outcome is unknown is reported to you, not sent again. Reads from your accounts are paced to the rate of a person using the service.

Your sign-ins and stored messages

Windows
Sign-ins, device secrets, saved state and cached pictures are encrypted with Windows' data protection for your user account, so other accounts on the PC can't read them.
Android
The server connection, your conversation list and pending sends are encrypted with a key held in Android's Keystore. The app turns off Android's cloud backup and device-to-device transfer, so none of it is copied off the phone.
Message Link Server
Every saved value is encrypted with a key file readable only by the server's own account, and conversation and message IDs in its history are stored as one-way codes. The server keeps its keys on a volume separate from its data.
Backups
Encrypted with AES-256-GCM under a password you choose, and every part is checked before anything is restored. They leave out live sign-ins, Messenger's encryption keys and the server's Tailscale identity, which are never copied.
Logs
They hold counts, states and one-way tags. They leave out message text, names, phone numbers, passwords and keys.

How your devices reach your server

Encrypted and pinned
Every connection uses TLS 1.2 or 1.3. Each app remembers your server's certificate fingerprint when it joins and refuses any other certificate, so a look-alike server can't stand in for yours.
A secret per device
Each device gets its own random 256-bit token. The server keeps only a hash of it, and removing a device on the server's page cuts it off at once.
Joining needs you
A device joins with a one-time pairing code that expires after 10 minutes and allows one guess per second, or by asking to join, which you approve on the server's page after comparing a matching code on both screens.
The server's page
It asks for a password of 12 characters or more and keeps only a slow, salted hash of it. Its sign-in cookie is HttpOnly, Secure and SameSite=Strict, every form checks where it came from, and the page runs no script from anywhere else. Showing a pairing code, approving a device or removing an account asks for the password again.
Home network and your tailnet only
The page, pairing and join requests answer only addresses on your home network or devices on your own Tailscale network. A request forwarded by a reverse proxy is refused, so the server can't be exposed to the internet by accident. Message Link Server for Windows listens on the PC itself only.
Checking the page's certificate
A browser can't pin the page's certificate the way the apps do, so it warns on the first visit. The server prints the certificate's fingerprint at start (server page certificate sha256=...), for you to compare once before you type the password.
Away from home
Your devices reach the server through your own Tailscale network. The server's door lets in only devices signed in to Tailscale as you (or, for a server you tagged, the ones your tailnet's access rules allow), and Tailscale's own logging is turned off.
Phone notifications
They are encrypted on your server with a key your phone made when it joined (the Web Push standard, RFC 8291) and travel through your own Firebase project. Google's servers carry them but can't read them.

Inside the server

One helper per service
Google Messages, Messenger, Google Voice and Instagram each run in their own helper program, connected to the server by private pipes that no other program can open. Sign-ins travel only through those pipes, never on a command line.
Downloads stay public
Pictures, files and link previews are fetched only from public internet addresses: a link can't make the server reach devices on your home network. Your sign-in goes only to the service's own sites. Sizes and image dimensions are capped before anything is decoded.
Chrome in its sandbox
The server signs in to some services through its own Google Chrome. Chrome runs every page in its sandbox, inside a container that runs as its own user with every Linux capability dropped and no way to gain new privileges.
Limits on what a device can ask
Message size, uploads, downloads running at once and connections per device are all capped, so a misbehaving device can't exhaust the server.

Protecting your accounts with the services

No unexpected actions
A send, reaction, edit or removal whose outcome is uncertain (the connection broke after it went out) is reported to you and never repeated automatically, so nobody gets a message twice.
Paced reads
Searches, background reads and reconnects are paced. Instagram reads have hourly limits, both in the background and when your devices ask, so your accounts are used at the rate a person would use them.
Sign-in on the services' own pages
You sign in on each service's own page, in a window that shows their address. The app reads only the sign-in cookies it needs from them, and the sign-in window can't reach the app's code.

On your PC and phone

Links
A link in a message opens only if it is a web or email address. A link whose words name a different site than it really goes to is shown as plain text.
Files you receive
They are saved with cleaned names and marked as coming from the internet, so Windows checks them before they run. Nothing opens by itself.
Notification actions on Android
Reply and Mark as read act only on the conversation the notification was for, and Mark as read needs the phone unlocked. A link from another app or website can open a texting conversation but never marks it read.
The terminal client
mlink removes control characters from message text, so a message can't take over your terminal.

Hermes Agent

Its key
Hermes's API key is sealed like a sign-in and is never shown on any device. The server talks only to the address you gave it and follows no redirects.
What it sees
Hermes sees only what you send it: your other conversations are never passed to it, and nothing it says can send, read or delete anything on your accounts.
Commands
When Hermes asks to run a command, it runs only if you approve it, and only that once. A command too long to show in full, or with characters that don't show, can only be denied in Message Link.

Updates and where the code comes from

Windows
Updates come only through the Microsoft Store, which checks the package's signature. Android updates come through Google Play.
The server image
It is built from pinned base images, with every dependency locked to an exact version and checked against its recorded hash. Dependencies are reviewed weekly and checked against known vulnerabilities before release.
Linux and Proxmox installs
They update themselves only to a package signed with Wrenchware's release key. A package that isn't, or that doesn't match its checksum, is refused before the server is touched.
The source
The source of the server and the service helpers is published with every release at github.com/wrenchware/message-link-source.

What it can't protect against

Someone using your unlocked PC or phone
They, or a program running as your Windows user, can see what you can. Lock your devices and keep them updated.
The machine your server runs on
Anyone with administrator access to it can reach what the server holds. Keep it updated and limit who can sign in to it.
The services themselves
What Google and Meta do with your messages is up to them. Their own privacy policies apply.
